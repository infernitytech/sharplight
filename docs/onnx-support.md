# ONNX support survey

Generated by `bench/onnx/make_report.py` from `bench/onnx/results/*.jsonl` (see *Reproducing* at the end). Survey only: nothing under `src/` or `tests/` was changed.

## Method

* Models live in `~/models/onnx/<name>/`; every model has an onnxruntime reference (CPU EP; the CUDA EP only where the CPU EP lacks a kernel) in the ZooTests fixture format: `~/models/onnx/ref/{,zoo/,survey/}<name>.json` + `.b1.in<k>.bin` / `.b1.out<k>.bin`. Inputs are fixed synthetic data (smooth images, random ids, ones masks); dynamic dims are pinned (sequence 16, KV past 8, images 224 unless the model needs another size) because the importer needs static non-batch dims. Merged decoders run with `use_cache_branch` pinned to 0.
* Sharplight: `bench/onnx/SurveyRunner` (import via `OnnxImporter`, `CompiledModel.Compile`, one process per model and provider). If a symbolic batch fails the harness retries with the concrete batch (that is noted). Parity = existing ZooTests criteria (manifest rtol/atol, or relative RMS for quantized models); `OK*` = outside the strict tolerance but relative RMS <= 5e-2 (quantized / fp16 models whose reference is itself noisy), `WRONG` = above that.
* Latency = min over N (<=30, >=3, 4 s budget) of `Run` + read back all outputs, batch 1. Sharplight Vulkan device 0 = RTX PRO 6000 Blackwell Max-Q (shared with the desktop: min times only), CPU = Ryzen 9 9950X (32 threads). ORT CPU = onnxruntime-gpu 1.31 CPU EP, ORT CUDA = CUDA EP (CUDA 13.5 / cuDNN 9.28 pip wheels), inputs pre-bound on the GPU and outputs copied to host, so both sides include the output read-back. TensorRT EP was not tried (the pip wheels lack libnvinfer; the CUDA EP works on this Blackwell GPU). Latencies that were measured in several sessions are reported as the minimum.

## Key findings

**Coverage.** 130 models (64 that already had ZooTests/reference fixtures + 66 new ones; 56 download entries from 54 Hugging Face repositories, 68 files; `bidaf-9` needs string inputs and `mnist-1` (opset 1) is rejected by onnxruntime itself, so neither has a reference) import, compile and run on both backends except 13 new models, all of which fail at *import* with a clear message. No existing model regressed: all 64 pre-existing models pass on CPU and Vulkan under the existing tolerances.
Of the 66 new models: 48 pass strictly on Vulkan, 2 are within 5e-2 relative RMS (fp16 / dynamic-int8 BERT), 3 are numerically off or wrong (see *Correctness issues*), 13 do not import.

**Blocked models (new).** `NonMaxSuppression` (SSD, Faster/Mask R-CNN, YOLOv3), `RoiAlign` (Faster/Mask R-CNN), `Loop` (YOLOv3 post-processing), ai.onnx-domain `SimplifiedLayerNormalization` + `com.microsoft.GroupQueryAttention` / `RotaryEmbedding` (Gemma-3, LFM2, Phi-3.5 from the onnxruntime-genai / Optimum "decoder_model_merged" exports), `STFT` (Kokoro TTS), data-dependent shapes (`NonZero`, `Range` with runtime limit: Grounding-DINO, GLiNER), `MatMulInteger` with a runtime B operand (activation x activation int8 attention in `bertsquad-12-int8`) and a conv whose weight is computed in-graph (weight-standardized BiT backbone in DPT-hybrid).
Only the *first failing op set* of a model is visible; models listed under the same op may fail on a second limitation afterwards (NMS-based detectors also produce data-dependent output shapes, which the importer's static-shape model may reject next).

**Notes on the headline gaps**
* `SimplifiedLayerNormalization` appears in the default ai.onnx domain in the onnxruntime-genai style exports (Gemma-3, LFM2, Phi-3.5). `src/Sharplight.Onnx` implements it only as `com.microsoft:SimplifiedLayerNormalization` (listed in `OnnxTranslator.Dispatch.cs`), so a domain-agnostic match would unblock the norm part of those three models; GroupQueryAttention (Gemma-3, LFM2) and RotaryEmbedding (Phi-3.5, whose attention is `com.microsoft:MultiHeadAttention`) are the real work.
* Models with `dim_param` batch axes that are reshaped across the batch (`Reshape [-1, 256]` etc.) fail with a symbolic batch and are retried with the concrete batch: 20 of 130 rows are marked `fb`. This is a limitation of the "outermost dim is the symbolic batch" convention, not an op gap.
* All other dynamic dims (sequence length, image size, KV-cache length) must be pinned through `OnnxImportOptions.InputShapes`; every dynamic-shape model in this survey was run that way (sequence 16/4, past 8, images 224-800). No model was tried with a varying sequence length at run time.
* `use_cache_branch` merged decoders (T5, distilBART, Florence-2, TrOCR, ViT-GPT2) import fine once the flag is pinned (`ConstantInputs`) and run on both backends with exact parity; they were run with the no-past branch (`use_cache_branch=0`).

**Quantized variants.** MatMulNBits (BERT `model_q4`, Qwen2.5 `model_q4`) matches ORT to ~1e-5 RMS; fp16 models (BERT, Qwen) import and run; QDQ int8 CNNs (ResNet50 / MobileNetV2 / EfficientNet-lite4 int8, existing + new) differ from ORT by 4-18% relative RMS on the logits for random input (the existing tests accept 0.25 RMS for them); DynamicQuantizeLinear/MatMulInteger BERT is within 2.6e-2 on Vulkan and 1.5e-3 on CPU. Sharplight CPU is 7-10x slower than ORT CPU on these int8 CNNs because it runs them as f32 after dequantizing at import.

**Latency overview.** Sharplight Vulkan is faster than ORT CPU on 108 of 117 comparable models (median Vulkan/CUDA = 1.9x, i.e. about half the speed of the CUDA EP on this GPU; some small decoder graphs are faster than ORT CUDA: Qwen2.5-0.5B fp16 / q4 with 4 new tokens and 8 past tokens at 0.5x / 0.6x of its time, T5 / TrOCR / ViT-GPT2 decoders at 0.7-0.8x). The outliers are single kernels, not general slowness (see the slow-model table): `topk` (~40 ms per launch, hit by every YOLOv10/YOLO26/RT-DETR style end-to-end head), `scatter_nd` (mobilevitv2), InstanceNorm on large maps (animegan), a 21 ms `softmax` over a 19-channel axis of 160000 positions (ResNet101-DUC). Transformer encoders at 16-197 tokens run 3-5x behind ORT CUDA because the f32 `matmul` kernel reaches only ~5 TFLOPS at 197 tokens (ViT 768->768: 44 us) and ~55 GB/s of weight streaming at 16 tokens (RoBERTa 768->768: 44 us, 3072->768: 170 us); the CUDA EP runs the same graphs through cuBLAS.
Vulkan compile time ("VK compile s" column, minimum over the sessions) is a separate cost: median 0.6 s once pipelines are cached (3.6 s in the first, cold session), but 50-100 s for conv-heavy models with many distinct shapes that did not get faster on repeat (DenseNet-9 83 s, PP-OCRv5 det 82 s, ResNet101-DUC 66 s, U2-Netp 63 s, Zipformer 60 s; up to 102 s on a cold run).

### Correctness issues found (new models)

| model | backend | observation |
|---|---|---|
| `bertsquad-12` | Vulkan | The graph returns its `unique_ids_raw_output___9:0` input through an `Identity`-like path as output `unique_ids:0` (int64): Vulkan returns `1065353216` = 0x3F800000, the bit pattern of the float `1.0f`, instead of the integer `1` (an i32 value went through an f32 `Scale` op and its float bits were read back as an integer). Other outputs match to 9e-7 RMS. |
| `bertsquad-12` | CPU | Does not compile: `Op Scale (node 796) is not supported on ... Scale: inputs must be f32 (or a convertible weight), got i32 for unique_ids_raw_output___9:0` - the same i32 pass-through reaches an f32-only op on the CPU backend. | `qwen2.5-0.5b.model_fp16` | CPU and Vulkan | rel. | `yolo26n` | CPU | rel. RMS 4.2e-2 on `pred_boxes` (Vulkan: 4e-7): end-to-end TopK head with near-tied scores on random input, likely a different ordering of tied rows on the CPU backend (not verified). |

## Reproducing

```sh
uv venv ~/venvs/ort --python 3.12 && source ~/venvs/ort/bin/activate
uv pip install onnx onnxruntime-gpu numpy huggingface_hub nvidia-cublas nvidia-cuda-runtime nvidia-cudnn-cu13 nvidia-cufft nvidia-curand nvidia-cuda-nvrtc
source bench/onnx/env.sh                       # LD_LIBRARY_PATH for the CUDA 13 / cuDNN 9 wheels
HF_HUB_DISABLE_XET=1 python bench/onnx/download_models.py
python bench/onnx/make_survey_refs.py          # ORT reference outputs -> ~/models/onnx/ref/survey
dotnet build bench/onnx/SurveyRunner -c Release
python bench/onnx/run_survey.py bench/onnx/results/sharplight_passN.jsonl     # Sharplight cpu+vulkan, one process per model
python bench/onnx/ort_bench.py bench/onnx/results/ort_passN.jsonl             # ORT CPU + CUDA latency
python bench/onnx/model_meta.py && python bench/onnx/make_report.py          # -> docs/onnx-support.md
# per-kernel GPU time of one model:  dotnet bench/onnx/SurveyRunner/bin/Release/net11.0/SurveyRunner.dll <manifest.json> vulkan --profile
```
Existing models are measured from their existing fixtures (`ref/*.json`, `ref/zoo/*.json`) without regenerating them. The harness reads the same manifest format as `ZooTests`.
