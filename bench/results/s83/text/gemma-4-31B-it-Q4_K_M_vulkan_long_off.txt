### 77.2 Window-sized KV caches for single-sequence sessions

Until now only the paged multi-sequence decoder (serving, BatchBench) gave sliding-window layers window-sized caches (§60); the
session path (CLI, Studio, one-slot serving) kept a row per position in every cache, so Gemma 4 31B (50 of 60 layers attend to a
1024-key window, 0.8 MB per token) needed 44.8 GiB at 32K.

 SessionKvLayout (Core, generic: any graph whose caches only sliding-window attention reads, MultiSequence.WindowedCaches): when
  the decode graph has such caches, CreateSession compiles the one-slot paged form of the graph (MultiSequence.Transform with
  window rows), the same kernels the serving decoder runs on CPU, Vulkan, CUDA and Metal. Both block tables are fixed and uploaded
  once: the full caches map position p to row p, the window caches block b to block b mod R of a ring of
  R = ceil((window + rows per pass − 1) / 16) + 1 blocks, every position one pass reads or writes. The session only appends, so no
  query ever sees a reused row; InferenceSession fills the sequence tables per pass (one run of slot 0).
 Used where the ring at most halves those caches (the one-slot paged form costs ~2 % of a CUDA decode step against the contiguous
  cache: Gemma 4 31B at 4K context 37.96 → 37.25 tok/s, GPU 26.13 → 26.68 ms; Vulkan 38.43 either way). Fallbacks to the plain
  graph: window_kv or paged_kv disabled, encoder-decoder graphs, graphs without a multi-sequence form, devices without the paged
  kernels. Nothing new is stored in .slm: the layout is derived from the stored graph at compile time.
 EstimateFootprint(slots: 1), the automatic rows per pass (SessionFootprint) and PlacementPlanner.Estimate count the ring.

### 77.3 The K-quant decode GEMM (CUDA, native_gemm_kquant)

At 9-64 rows the K-quant projections ran gemm_cm2 with split-K on dequantized tiles, at 285-390 GB/s on this card (§74's profiles:
Qwen3-8B gate / up [4096 → 12288] Q4_K 99.3 µs at 32 rows). gemm_kq_native.cu (Shaders, compiled by NVRTC, selected in
GraphLowerer.KQuantGemm.cs beside the f16 decode form, multi-output form for q / k / v of one format):

 A block covers 16, 32 or 64 token rows (by batch) and 64 weight rows; its eight warps take 8 weight rows each and every token row,
  so each weight value is dequantized once per block. A K step is one 256-value superblock: cp.async copies the activation rows
  (four 64-value swizzled sub-tiles, read by ldmatrix) and the raw Q4_K / Q5_K / Q6_K blocks of the 64 rows (each row's 16-byte
  window around its block: Q6_K rows of 210-byte blocks start at any even byte) into a ring of 2-4 stages (≤ 96 KiB). Each thread
  builds its mma.sync.m16n8k16 B fragments straight from the raw codes (two codes per byte_perm, exact f16 integers from the
  0x6400 bias trick, then one f16 FMA with the sub-block scale and minimum; Q4_K / Q5_K scales unpacked with word operations), f32
  accumulation. No weight is ever written back as f16.
 K split only where the grid is small or its last wave nearly empty (Gemma's [21504 → 5376]: 84 blocks on 82 SMs, 220 → 182 µs
  split in two), reduced in the last block of each tile in slice order (deterministic, counters self-resetting).
 Batches of 9-16 rows of K-quant matmuls leave the skinny GEMM for it (SkinnyMaxRowsFor), the dual gate / up form included (two
  launches and the activation product: steps at 16 sequences Qwen3-8B 9.87 → 8.35 ms, Qwen3.8 27B 35.75 → 30.05, Gemma 4 31B 43.64
  → 38.12 against keeping the skinny dual form, ab22). Decode batches whose generated
  split would be 1 (wide matrices, e.g. Qwen3.8 27B gate / up [5120 → 17408] at 16 rows: 165 µs each on unsplit gemm_cm2) are routed
  to the split-K emission, where the K-quant GEMM takes them (NativeKQuantPlanSplit).

### 77.4 Measured and not kept

 Split rings (v4: 64-value activation stages in a shallow ring, weight superblocks copied 2-3 ahead in their own slots): more
  barriers per superblock; Q6_K [12288 → 4096] at 32 rows 76.0 against 60.4 µs, Q4_K [4096 → 12288] 56.6 against 52.4.

 Per-value scale lookups for Q4_K (get_scale_min_k4 per sub-block): 54.6 against 52.4 µs with word-wise unpacking.
 64-row token tiles below 33 rows (two stages only: 96-107 µs for the 32-row shapes above) and two 32-row tiles at 64 rows
  (each block re-reads the weights: 89.5 / 115.1 against 82.1 / 89.7 µs).
 The wave-count K split (WaveFillSplit) on grids of 1.5-3 waves: memory-bound blocks of a partial last wave run faster, so
  splitting [4096 → 12288] (192 blocks) cost 5 %; the split is kept only for nearly empty last waves and small grids.
 Batches of 9-16 rows on unsplit gemm_cm2: capping the skinny GEMM first sent wide gate / up matrices whose generated split is 1
